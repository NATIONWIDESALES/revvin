- sitemap.xml and llms-full.txt are generated at build by plugins/sitemap.ts and plugins/prerender.ts from PRERENDER_ROUTES; never hand-write public/sitemap.xml. Why: the sitemap cannot drift from the built, indexable pages.
- Brand colours are HSL tokens in src/index.css (forest, green, sign, paper, line) mapped to shadcn vars; marketing layout classes use the mk-/rf-/yard- prefixes there. Why: one source for the yard-sign design across pages.
- Business dashboard navigation is the DashboardShell rail; tab ids and next-step/stat logic live in src/lib/dashboardHome.ts. Why: deep links (?tab=) and Home numbers stay testable in one place.
- Public routes are server-rendered at build (src/entry-server.tsx via plugins/ssr.ts) into each prerendered document with data-ssr="1"; src/main.tsx hydrates those and client-renders everything else. Referral pages get their business row through window.__REVVIN_SSR__ (src/lib/ssrData.ts). Why: crawlers and first paint get the real page, and hydration needs identical first-render data.
- Fixed public page titles/descriptions live in src/content/pageMeta.ts and are read by both seoRoutes.ts and each page's SEOHead; src/test/seo-pass.test.ts enforces lengths. Why: prerendered head and hydrated head cannot disagree.
- The backend client is loaded with loadSupabase() from src/lib/supabaseLazy.ts, never statically imported by marketing code; tslib is pinned to the react chunk in vite.config.ts. Why: keeps the backend bundle off the initial download of marketing pages.
- Fonts are self-hosted from src/assets/fonts with metric-matched fallbacks in src/index.css; the prerender preloads the two hero weights and inlines critical CSS (beasties) on server-rendered documents. Why: no third-party render-blocking stylesheet.
- Only Home and Pricing give hero font preloads high fetch priority and entry/module preloads low priority. Why: reduce startup contention on text-led pages without deferring hydration or changing other routes.
- Guides are data in src/content/guides.ts (+ guidesNew.ts) with optional table, copyGroups, terms and sources rendered by GuidePage and flattened into PrerenderRoute sections; every "Related" block comes from src/content/related.ts and trade-page extras from src/content/tradeExtras.ts. Why: one content source feeds the page, prerender, sitemap, RSS and llms-full.txt.
- Public author identity and team copy come from src/config/brand.ts; the prerender validates public source and generated text before writing it. Why: runtime, structured data and generated documents cannot drift back to personal branding.
- Instant-preview choices use lightweight previewTrades shared by industries; session/query data is validated before signup and never copied into analytics. Why: keeps full trade articles off the hero bundle and typed business data out of measurement.
- First-touch acquisition is captured at public document startup only in sessionStorage; signup prefers preview data, then first touch, then its current URL. Why: internal navigation and later campaigns must not replace the original landing attribution.
- Pro entitlements come from fn_effective_plan; server-created trial dates are immutable to owners and existing businesses are not backfilled. Why: paid plan derivation remains untouched while trial gates agree on one authority.
- Meta browser code runs only in the no-referrer ad-events document after permission and delayed activation, exchanging fixed event names and a validated registration event ID only. Why: provider code must never observe signup fields, personal query strings or private SPA routes.
- Meta registration IDs and payload construction share the pure _shared/meta-registration module; server transport goes only through the linked Meta ads connection gateway (no Meta token in app code) and hashed email stays disabled. Why: browser/server dedup must agree without exposing credentials or enabling unapproved matching.
- Meta signup eligibility uses authenticated metadata only for signup intent and excludes known demos without requiring a business row; metadata never grants access. Why: asynchronous row availability must not suppress new-account measurement.
- Meta click handoff forwards only a validated session fbclid after permission; signup/welcome preview URLs are cleaned only after verified session storage. Why: attribution must not expose personal preview data or lose the fallback handoff.
- Meta bridges survive eligible SPA navigation; departing bridges drain only already-authorized events until SDK dispatch acknowledgments or a five-second deadline, with independent immediate withdrawal listeners. Why: navigation must not discard queued conversions or let grace periods bypass refusal; acknowledgments do not prove Meta receipt.

- Security-sensitive submissions and referrer actions use bounded, ownership-checking RPCs; unrestricted writer functions remain service-only. Why: public and authenticated clients cannot forge audit, notification, lead identity or job-ask records.
- Referrer email trust requires an OTP session or a completed email challenge, not auto-confirmed password signup. Why: preserve instant business signup without exposing another person's referrals.
- Referral search approval is separate from publication and defaults off. Why: moderation must not break the live referral form.
- Publish failure analytics use an allowlisted reason classifier shared with the privacy filter; onboarding must confirm an awaited owner save returned required fields before publishing. Why: failures stay diagnosable without personal data or silent zero-row writes.
- Onboarding derives draft links from the final business name using validated name words and numeric collision suffixes, preserves published links, and saves typed city independently of Places. Why: edits before publication must not leave owner-name links or require autocomplete for city persistence.
- SQL email regression tests resolve the latest function definition in migration order and execute payload capture in isolated PostgreSQL. Why: historical migrations remain immutable while active writers meet the delivery contract.

- Checkout price selection is explicit-versioned; absent version uses legacy IDs and unknown versions fail closed. Why: live functions and unpublished price copy deploy separately.
- Temporary sale UI starts hidden and reads server-clock state from checkout GET; promo.ts selects one version-gated coupon. Why: cached pages and client clocks cannot extend sale pricing or stack discounts.
- Billing pickers share useBillingPlan; pending and explicit choices override asynchronous sale defaults. Why: sale refreshes must not change a customer's selected billing period.
- Sale chrome lives above navigation in Layout with an explicit marketing/owner route gate; the first-visit dialog is lazy and browser-only. Why: referrer routes and prerendered documents must never show SaaS sale interruptions.
- Sale popup paid-ad suppression is a session-only boolean in salePresentation, with an in-memory fallback; banner eligibility is independent. Why: paid landing visits must not trigger upgrade interruptions later in navigation or retain click identifiers.
- Automatic job asks use fn_effective_plan at creation and immediately before scheduled delivery; paused rows and connections remain stored. Why: trial expiry cannot silently send a Pro-only ask.
- Pricing FAQ pairs live in shared content consumed by the page and prerender route; collapsed answers stay mounted but hidden. Why: static HTML and FAQPage schema must describe the same accessible answers.
- Lifecycle Pro email copy uses trialEmailData from stored plan and future trial end, independently of effective-plan selection. Why: free trials must not be described as purchases without changing delivery rules.

- Same-user auth events preserve user object identity while updating sessions; account loaders depend on user IDs and loaded business refreshes stay mounted. Why: token refresh and tab focus must not clear unsaved forms or open dashboard controls.

- Dashboard Pro upsell copy resolves features by label, never by list position. Why: feature reordering must not change the upgrade promise.
- Job-delay backfills keep original values in a service-only, RLS-locked rollback table. Why: reversing the backfill must not reset preexisting custom delays.
- Operational failures use reportFailure and private rate-limited RPCs, the existing email queue, and the retention audit trigger; admin reads use an admin-checked RPC. Why: customer-linked errors must not enter visitor analytics or expose private records.
- The email queue accepts alternate managed service credentials only after server-side Auth admin verification; never authorize decoded JWT roles alone. Why: dispatcher and runtime credentials can differ while forged claims must fail closed.
- Origami runs once per document in an opaque, no-referrer sandbox removed on non-marketing routes, with browser opt-out and bot gates. Why: its automatic SPA listener and cookie writer must never access private pages or site storage.
- Admin access uses caller-scoped has_role with live verified TOTP factors and JWT AAL2; the UI gates before mounting admin data and allows enrollment before the first verified factor. Why: service-role lookups bypass user assurance and must not authorize admin actions.
- Private and referral routes block framing before initial React render and on SPA navigation. Why: client guards compensate for missing host frame headers, and no referral embedding feature exists.
- Security dependency overrides pin patched transitive packages; deployment-specific remote imports must be reviewed separately. Why: a browser lockfile does not update remote edge dependencies.
- Lazy/Vite recovery uses a 30-second path guard and deferred chunk_reload reports; crash stacks keep bounded file:line in message/code; Slider supplies missing ResizeObserver and optional observers skip. Why: recover once and diagnose safely in reduced-feature browsers without migrations.
